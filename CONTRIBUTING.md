# Contributing to InstantReplay

Thanks for your interest! InstantReplay is an early-stage project maintained by one developer, so small, focused contributions are the easiest to review. For anything larger than a bug fix, please open an issue first so we can agree on the approach.

The design is in [docs/SPEC.md](docs/SPEC.md) and the current roadmap in [docs/PLAN-v0.1.md](docs/PLAN-v0.1.md).

## Project layout

The repository is a [pub workspace](https://dart.dev/tools/pub/workspaces) with three members:

| Path | What it is |
|---|---|
| `app/` | The Flutter app (Android + web): Camera and Viewer roles |
| `packages/replay_capture_android/` | Flutter plugin (Kotlin): Camera2, GL fan-out, MediaCodec, fMP4 ring buffer, WebRTC sender |
| `packages/replay_protocol/` | Pure Dart: DTOs, WebSocket messages, protocol versioning (shared by the native app and the web build) |
| `docs/` | Specification, plan and developer guides |

## Toolchain

- Flutter **3.44.1** stable (Dart **3.12.1**)
- JDK **17**
- Android SDK **36** (compile SDK); the app's `minSdk` is **29** (Android 10)
- An Android device for anything that touches capture, network or UI. See [docs/dev-setup.md](docs/dev-setup.md) for the wireless device loop (no USB cable needed).

## Build and test

From the repository root:

```sh
flutter pub get          # resolves all workspace members
flutter analyze          # must be clean
```

Dart and Flutter tests:

```sh
cd packages/replay_protocol && dart test
cd app && flutter test
```

Build the APK with the build script, not plain `flutter build apk`:

```sh
tool/build_apk.sh               # Linux/macOS/CI; add --release for a release APK
pwsh tool/build_apk.ps1         # Windows; add -Release for a release APK
```

Why: the Camera serves the web Viewer to browsers on a LAN with no Internet (SPEC §6), so the APK must carry the Flutter **web** build of the same app. The script runs `flutter build web --release --no-web-resources-cdn` (CanvasKit bundled locally instead of loaded from Google's CDN), fails if the bundle references an external host (gstatic, googleapis, Google Fonts, unpkg, jsdelivr), copies `app/build/web` into the Android native assets folder `app/android/app/src/main/assets/web_viewer/` (git-ignored, generated), then runs `flutter build apk`. At runtime `MainActivity` extracts it to the app's files directory. A plain `flutter build apk` still works but produces an APK without the web Viewer.

Keep the web build offline: the UI font (Roboto, `app/fonts/`) is bundled as a Flutter font rather than fetched from Google Fonts, and `app/web/flutter_bootstrap.js` points the engine's fallback-font URL at a local path. The bundle is deliberately not a Flutter asset (`pubspec.yaml` `assets:`): the web build would then include the previous bundle recursively.

Kotlin unit tests. The Gradle wrapper and plugin wiring in `app/android` are generated by the first Flutter build, so build once before running Gradle directly:

```sh
tool/build_apk.sh                        # once (or: cd app && flutter build apk --debug)
cd app/android && ./gradlew :replay_capture_android:testDebugUnitTest
```

Run on a device:

```sh
cd app && flutter run
```

## Workflow

- `main` stays releasable. Work happens on one branch per task, named after its milestone (`m2/outbox`, `m3/ws-hub`, …), and lands through a pull request that is squash-merged.
- Reference the plan task in the PR (for example "M2.3") when there is one.
- Keep PRs small: one task, one concern.

### Definition of done

A change is done when:

1. `flutter analyze` is clean.
2. Pure logic has unit tests.
3. CI is green.
4. If it touches capture, network or UI, it has been checked on a real device (the reference device is a Redmi Note 12 Pro 5G).

## Code style

- Code, comments, commit messages and docs are in **English** (the README also has a Spanish version).
- User-facing strings go through the ARB files (`app_en.arb` and `app_es.arb`); never hard-code them, and add both languages.
- Follow the analyzer rules in `analysis_options.yaml` and format with `dart format`.
- Match the surrounding code: naming, feature-first structure (`data/ domain/ presentation/`), Riverpod patterns.
